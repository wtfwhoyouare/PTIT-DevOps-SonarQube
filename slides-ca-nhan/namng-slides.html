Ứng dụng web PHP 8.2 + MariaDB 10.11 chạy trên Docker. Khách hàng tra cứu cảng biển, theo dõi vận đơn, bình luận trên đơn hàng; quản trị viên xem dashboard và xuất báo cáo.

③ Quy trình phát hành thay đổi (phần tôi phụ trách)

Nhánh cá nhânnamng, haind, manhdx, anhld, mainp
commit theo Conventional Commits
→
PR vào dev[namng] fix(ci): ...
Stage 1 Policy Guard
Stage 2 SonarQube + Semgrep
→
PR dev → mainrelease: v1.1.1 - ...
Stage 1 + Stage 3 smoke test
→
Push lên mainStage 4 tự động SSH vào VPS, kéo image từ GHCR, chạy production

Ba nguyên tắc bắt buộc

  • Không commit hoặc push trực tiếp lên main và dev
  • PR của thành viên chỉ được hướng vào dev
  • main chỉ nhận PR phát hành từ dev, tiêu đề theo SemVer

Vì sao đây là vấn đề an toàn

Mỗi lần có code mới trên main, Stage 4 tự động triển khai lên máy chủ đang giữ dữ liệu khách hàng. Nếu đi tắt được vào main, code chưa ai rà soát và chưa qua SAST sẽ chạy thật trên production.

Phát hiện vi phạm ở 3 lớp, sớm nhất có thể

Lớp 1 · máy trạm

Git hook commit-msg

Kích hoạt bằng git config core.hooksPath .githooks. Mỗi lần commit, hook gọi policy_guard.py; tiêu đề sai chuẩn thì huỷ commit ngay trên máy.

Lớp 2 · Stage 1 CI

Policy Guard trên GitHub Actions

  • PR vào main mà nhánh nguồn khác dev: chặn
  • Tiêu đề PR vào dev / main sai mẫu: chặn
  • Quét mọi commit trong sự kiện push

Stage 1 thất bại thì Stage 2–4 bị bỏ qua.

Kiểm tra bằng GitHub API

Vi phạm nguyên tắc bảo vệ dữ liệu ngay từ thiết kế

Nghị định 13/2023/NĐ-CP

  • Điều 26: biện pháp bảo vệ dữ liệu cá nhân phải được áp dụng ngay từ khi bắt đầu và trong suốt quá trình xử lý. Để code chưa kiểm định chạy trên hệ thống xử lý dữ liệu là bỏ trống biện pháp này ở khâu phát hành.
  • Điều 27: bên xử lý phải có biện pháp quản lý và kỹ thuật bảo vệ dữ liệu cá nhân cơ bản. Quy chế phân nhánh chỉ ghi trên giấy mà không ép buộc bằng kỹ thuật thì chưa đáp ứng.

GDPR

  • Article 25 (1): data protection by design and by default: biện pháp kỹ thuật phải có sẵn trong hệ thống, không phụ thuộc vào việc người dùng tự giác.
  • Article 32 (1)(b): bảo đảm tính toàn vẹn liên tục của hệ thống xử lý dữ liệu.
  • Article 32 (1)(d): có quy trình kiểm tra, đánh giá định kỳ hiệu quả của biện pháp kỹ thuật, ở đây là bộ test và pipeline chạy mỗi lần thay đổi.

Hậu quả nếu bị khai thác: backdoor hoặc đoạn code đọc bảng users (mật khẩu, email, api_key) có thể lên production trong vài phút, không để lại PR hay review nào để truy vết.

YC4Demo: đoạn code phát hiện lỗi

ci/policy_guard.py: kiểm tra luồng Pull Request

def validate_pull_request_event(event_data):
    pr = event_data.get("pull_request", {})
    base_branch = pr.get("base", {}).get("ref", "")
    head_branch = pr.get("head", {}).get("ref", "")
    pr_title = pr.get("title", "").strip()

    # 1. main chỉ nhận PR từ dev
    if base_branch == "main" and head_branch != "dev":
        log_error("Vi phạm luồng phân nhánh", err_msg)
        return 1

    # 2. PR vào dev: [mã_nhánh] loại(phạm_vi): mô tả
    if base_branch == "dev" and not PR_DEV_REGEX.match(pr_title):
        log_error("Sai quy ước đặt tên PR vào dev", err_msg)
        return 1

    # 3. PR vào main: release: vX.Y.Z - mô tả
    if base_branch == "main" and not PR_MAIN_REGEX.match(pr_title):
        log_error("Sai quy ước đặt tên PR vào main", err_msg)
        return 1
    return 0

File JSON của sự kiện mà GitHub đặt ở $GITHUB_EVENT_PATH: nhánh nguồn, nhánh đích, tiêu đề PR, danh sách commit.
